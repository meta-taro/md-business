なぜ文書は嘘になるのか

設計が変わる → 仕様書は共有ドライブの .docx → AI が開けない → コードから推測する → 文書が実物と食い違う → 誰も開かなくなる。

仕事のほとんどは、AI が読めるテキストへ移った。残っているのは「その仕事がどうあるべきかを書いた文書」だけ。 Word・Excel・PDF や多くの文書 SaaS が AI に渡すのは、中身の見えないバイナリか、差分の取れない API になる。 だから AI はコードのほうを見て、文書はそこから離れていく。

md-business は、その正本を Markdown へ移す OSS（MIT）。請求書・検証シート・基本設計書・ API 仕様書・DB 設計書を、YAML frontmatter と JSON Schema 検証付きの Markdown で持つ。 人が読む形式を取り上げはしない。人は PDF・Google Sheets・専用ビューワーで読み、 AI は同じファイルを読み、直し、検証し、差分を出す。

どう繋がっているか

Markdown                       ← 正本。1 文書 1 ファイル
   ↓
JSON Schema 検証               ← 壊れた請求書は、誰かが押印する前に落ちる
   ↓
AI が直す                      ← MCP 経由で、いま開いているフォルダの中を
   ↓
git diff でレビュー・承認      ← どの行が変わったかが見える
   ↓
PDF・Sheets・Chrome・デスクトップ ← 人が実際に読む形

要点は最後の行。文書は、人が信用できる形で読んで初めてレビューされたことになる —— A4 の請求書、表になった検証シート。下が Markdown であることは、そこを変えない。

いま書ける文書

invoice 実装済み

適格請求書。登録番号・税率ごとの内訳・合計の自動計算まで含む。

spec 実装済み

基本設計書。システム概要・画面・データフロー・受入条件を節として持つ。

test-spec 実装済み

検証シート。ケースごとの OK / NG / 保留を表で埋め、Google Sheets と往復できる。

api-spec 未実装

API 詳細設計書。エンドポイントのリクエスト / レスポンス定義と例。

db-spec / nosql-db-spec 未実装

RDB / NoSQL の DB 設計書。項目単位の定義とリレーション。

zumen と組み合わせる

zumen — AI が描き、人が直し、その直しが壊れない構成図

構成図をテキストで持つエディタ。AI が描いた図を人が 1 か所だけ直しても、 次に AI が描き直したときにその直しが消えない。MCP の口を持つので、エージェントに直接描かせられる。

考え方が同じなので、そのまま噛み合う。md-business は文書を、zumen は図を、 どちらも人と AI が同じテキストを直す正本として持つ。設計書の本文は md-business、 その中の構成図は zumen —— 文書と図が別のファイル形式に分かれず、どちらも同じリポジトリで差分が取れる。
