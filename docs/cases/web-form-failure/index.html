申込フォームが一部の人だけ送れない

架空の事例です。会社・人・数字はすべて作りものです
使うもの
利用者のブラウザで保存した通信の記録（.har）、Web サーバーとアプリのログ、MCP の read_har・search_lines・build_timeline・save_evidence、調査報告書の書式
見つかるもの
添付ファイルが 1MB を超えると、アプリに届く前に手前のサーバーが 413 で断っている。フォームの説明は「5MB まで」
直し方
手前のサーバーの上限をフォームの説明と揃える。揃えるまでの間は、フォーム側で 1MB を超えたら送る前に知らせる

起きていたこと

ある会社の資料請求フォームで、「送信を押すと『送信できませんでした』と出る」という問い合わせが週に数件届いていた。 社内で試すと送れる。届いた問い合わせの多くには、名刺や見積書の画像が添付されていた。

1. 失敗した往復を特定する

問い合わせてきた人に、ブラウザの開発者ツールで通信の記録（.har）を保存して送ってもらった。 エージェントは read_har で全文を開かずに概況だけを読む。

件数 38 / ステータス別 200: 36, 304: 1, 413: 1
遅い順 1 位  POST /api/inquiries  413  1.2 秒  要求本文 3.4MB

その 1 件を index で指して中身を読むと、応答の Server がアプリのものではなく、 本文はアプリのエラー画面ではない短い HTML だった。アプリまで届いていない。 Cookie や Authorization は、読んだ時点で伏せ字になっている。

2. ログで裏を取る

Web サーバーとアプリのログは数十万行ある。エージェントは全文を読まず、search_lines で当たりを付ける。

proxy-error.log:18342  client intended to send too large body: 3565158 bytes

同じ時刻のアプリのログに、この要求は 1 行も無い。2 本のログを build_timeline で時刻順に混ぜると、 断られた要求の前後でアプリ側が何も受け取っていないことが、出どころと行番号付きで並ぶ。 過去 30 日を数えると、413 は 23 件で、すべて 1MB を超える添付だった。

3. 根拠を残して報告書にする

報告書から指せるよう、save_evidence で抜粋を保存する。HAR の 1 件が evidence/EV-001.md、 2 本のログを並べた区間が evidence/EV-002.md になる。会話の中だけにある抜粋は、後から確かめられないので根拠にしない。

報告書は調査報告書の書式（investigation/v1）で書く。所見ごとに根拠を指す。

所見:
  - 番号: F-01
    要約: 1MB を超える添付付きの送信が、アプリに届く前に 413 で断られている
    深刻度: 高
    根拠:
      - evidence/EV-001.md
      - evidence/EV-002.md
  - 番号: F-02
    要約: フォームの説明は「5MB まで」で、手前のサーバーの上限（1MB）と食い違っている
    深刻度: 中
    根拠:
      - evidence/EV-002.md

エージェントが書くときに書式の検査が走る。根拠を 1 つも指していない所見は、深刻度にかかわらずそこで落ちる。

4. 直す

  • 手前のサーバーの上限を、フォームが約束している 5MB に揃える。
  • 揃えるまでの間は、フォームが送る前にファイルの大きさを見て、超えていればその場で知らせる。
  • 社内で再現しなかったのは、試した人が小さな画像しか使っていなかったため。検証シートに「1MB を超える添付」の行を足す。

この流れで変わること

調べた人の頭の中にしか無かった「なぜそう言えるか」が、報告書と根拠のファイルとして Git に残る。 次に同じ問い合わせが来たとき、読む人は会話の履歴ではなく、報告書の所見から根拠をたどれる。
